# LocalAgent — Distributed Claude Code Task Runner

A system for distributing Claude Code tasks across multiple desktop/workstation workers via RabbitMQ, with HTTP-proxied queue access and pluggable output emitters.

## Architecture Overview

```
Producer (HTTP)
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│ VPS (Docker Compose)                                     │
│                                                          │
│  ┌─────────────┐       ┌──────────────────────────────┐  │
│  │  API Server  │◄─────│  RabbitMQ (internal only)     │  │
│  │  (Fastify)   │─────►│                              │  │
│  └──────┬───────┘       │  tasks exchange → task queue │  │
│         │               │  jobs exchange  → job queue  │  │
│         │               │  results exch.  → results q  │  │
│         │               └──────────────────────────────┘  │
│         │                                                 │
│  ┌──────┴───────┐                                        │
│  │ Worker        │  (--mode emit)                         │
│  │ Emitter only  │  consumes results, sends Telegram/Lark │
│  └───────────────┘                                        │
└──────────────────────────────────────────────────────────┘
    ▲
    │ HTTP polling (API key auth)
    │
┌───┴──────────────┐   ┌──────────────────┐
│ Desktop Worker A  │   │ Desktop Worker B  │
│ --mode enrich,    │   │ --mode enrich,    │
│        execute    │   │        execute    │
│ (own Claude sub)  │   │ (own Claude sub)  │
└───────────────────┘   └──────────────────┘
```

## Shared Contract (`packages/shared/`)

### Task Type Definitions

Each task type is registered as an object:

```typescript
interface TaskTypeDefinition<T extends z.ZodType> {
  name: string;                    // Routing key, e.g. "code_review"
  payloadSchema: T;                // Zod schema for the raw task payload
  promptTemplate: string;          // Template string filled by enricher
  allowedTools?: string[];         // Claude Code tools to permit
  maxTokens?: number;
  timeout?: number;                // ms, default 3_600_000 (1 hour)
}
```

### Message Schemas (Zod)

**TaskMessage** — published by API server, consumed by enricher workers:

```typescript
{
  taskId: string;          // UUID, generated by API server
  type: string;            // Task type name (routing key)
  outputType: string;      // "telegram" | "lark"
  outputMeta: object;      // Per-output-type metadata (chat ID, webhook URL, etc.)
  payload: object;         // Raw task payload, validated against task type schema
}
```

**JobMessage** — published by enricher, consumed by executor workers:

```typescript
{
  taskId: string;
  type: string;
  prompt: string;          // Fully assembled prompt string
  allowedTools?: string[];
  maxTokens?: number;
  timeout: number;         // ms
  outputType: string;
  outputMeta: object;
}
```

**ResultMessage** — published by executor, consumed by emitter workers:

```typescript
{
  taskId: string;
  status: "ok" | "error";
  output: string;          // Claude's output or error message
  outputType: string;
  outputMeta: object;
}
```

### Output Type Registry

Maps `outputType` to its `outputMeta` Zod schema:

```typescript
{
  telegram: z.object({ chatId: z.string() }),
  lark:     z.object({ webhookUrl: z.string() }),
}
```

### Constants

Exchange names, queue names, routing key helpers — single source of truth imported by all packages.

## API Server (`packages/api-server/`)

Fastify HTTP server. Connects to RabbitMQ internally via AMQP. Exposes all queue operations over HTTP.

### Authentication

API key auth via `Authorization: Bearer <api-key>` header on all endpoints. Keys stored in config file or env vars as a simple key-to-label map.

### Endpoints

#### Task Submission

```
POST /tasks
Body: { type, outputType, outputMeta, payload }
Response: { taskId }

Validates payload against shared schema, generates taskId, publishes TaskMessage
to tasks exchange with routing key `task.<type>`.
```

#### Queue Proxy

Generic endpoints that proxy RMQ queues over HTTP. Workers poll these.

```
GET  /queues/:queueName/consume
Response: { deliveryTag, message } or 204 (empty)

Dequeues one message from the named queue. Message remains unacked in RMQ
until the worker confirms via /ack or /nack. Server maintains an in-memory
map of deliveryTag → AMQP channel for in-flight messages.
```

```
POST /queues/:queueName/ack
Body: { deliveryTag }

Acks the message on RMQ. Removes from in-flight map.
```

```
POST /queues/:queueName/nack
Body: { deliveryTag }

Nacks with requeue: false. Message is dropped.
```

```
POST /queues/:queueName/publish
Body: { routingKey, message }

Publishes a message to the exchange associated with the named queue.
```

#### Health

```
GET /health
Response: { status: "ok" }
```

### In-Flight Message Management

The server holds unacked AMQP messages in memory, keyed by `deliveryTag`. If a worker disappears (no ack/nack within the task's configured timeout + a buffer), the server nacks the message with `requeue: true` so another worker can pick it up.

## Worker (`packages/worker/`)

### Modes

Controlled by `--mode` flag. A worker can run one or more modes:

- **`enrich`** — polls task queue, resolves context, builds prompt, publishes job
- **`execute`** — polls job queue, spawns `claude -p`, publishes result
- **`emit`** — polls results queue, dispatches to emitter adapter

Typical deployments:
- Desktop workers: `--mode enrich,execute`
- VPS emitter worker: `--mode emit`

### Hexagonal Architecture

**Ports** define interfaces. **Adapters** implement them. **Core** contains domain logic that depends only on ports.

#### Ports

| Port | Methods | Purpose |
|------|---------|---------|
| `QueuePort` | `consume()`, `ack(tag)`, `nack(tag)`, `publish(queue, msg)` | Queue operations via HTTP |
| `EmitterPort` | `emit(result): Promise<void>` | Send result to a chat platform |
| `TaskResolverPort` | `resolve(task): Promise<context>` | Fetch external context for enrichment |
| `ExecutorPort` | `execute(job): Promise<result>` | Run Claude Code |

#### Adapters

- **`http-queue`** — implements `QueuePort` by polling `GET /queues/:name/consume` every 5 seconds and calling ack/nack/publish endpoints on the API server.
- **`emitters/telegram`** — implements `EmitterPort` using Telegram Bot API. Reads `outputMeta.chatId`.
- **`emitters/lark`** — implements `EmitterPort` using Lark webhook. Reads `outputMeta.webhookUrl`.
- **`resolvers/github`** — implements `TaskResolverPort` for fetching PR diffs, file contents from GitHub.
- **`executor/claude-cli`** — implements `ExecutorPort` by spawning `claude -p "<prompt>" --output-format stream-json`. Kills the subprocess with `SIGKILL` after the configured timeout.

#### Core

- **`enricher.ts`** — takes a `TaskMessage`, calls `TaskResolverPort.resolve()` to get context, fills the prompt template from the task type definition, produces a `JobMessage`.
- **`executor.ts`** — takes a `JobMessage`, calls `ExecutorPort.execute()`, wraps the output in a `ResultMessage` with `status: "ok"` or `status: "error"`.
- **`pipeline.ts`** — starts polling loops for each enabled mode, wires consume → process → publish → ack for each stage.

#### Dependency Injection

Constructor injection, no framework. `main.ts` reads `--mode` and config (API server URL, API key, emitter tokens), instantiates the relevant adapters, injects them into core classes, and starts the pipeline.

### Error Handling

- On Claude CLI failure (non-zero exit or timeout): worker publishes a `ResultMessage` with `status: "error"` and the error details as `output`, then acks the job message. The emitter worker sends the failure notification to the user's chat.
- No automatic retries. Failures are reported immediately.
- On network errors (can't reach API server): worker logs and retries the poll on the next interval.

### Task Timeout

Default: 1 hour (3,600,000 ms). Configurable per task type in the shared contract. The executor spawns the Claude CLI subprocess and starts a timer. If the timer fires before the process exits, it sends `SIGKILL` to the process group and treats it as a failure.

## RabbitMQ Topology

Declared via `definitions.json`, loaded on broker startup.

### Exchanges

| Exchange | Type | Purpose |
|----------|------|---------|
| `tasks.exchange` | topic | Routes task messages by type |
| `jobs.exchange` | topic | Routes job messages |
| `results.exchange` | topic | Routes result messages by output type |

### Queues

| Queue | Bound To | Routing Key |
|-------|----------|-------------|
| `tasks.queue` | `tasks.exchange` | `task.#` |
| `jobs.queue` | `jobs.exchange` | `job.#` |
| `results.queue` | `results.exchange` | `result.#` |

### Message Durability

All exchanges are durable. All queues are durable. Messages are published as persistent (`deliveryMode: 2`).

## Docker Compose (VPS)

```yaml
services:
  rabbitmq:
    image: rabbitmq:3.13-management-alpine
    # No exposed ports — internal only
    volumes:
      - ./rabbitmq/definitions.json:/etc/rabbitmq/definitions.json
      - ./rabbitmq/rabbitmq.conf:/etc/rabbitmq/rabbitmq.conf

  api-server:
    build: ../../packages/api-server
    ports:
      - "3000:3000"
    environment:
      - AMQP_URL=amqp://admin:password@rabbitmq:5672
      - API_KEYS=key1:label1,key2:label2

  emitter-worker:
    build: ../../packages/worker
    command: ["node", "dist/main.js", "--mode", "emit"]
    environment:
      - API_SERVER_URL=http://api-server:3000
      - API_KEY=key1
      - TELEGRAM_BOT_TOKEN=...
      - LARK_WEBHOOK_URL=...
```
