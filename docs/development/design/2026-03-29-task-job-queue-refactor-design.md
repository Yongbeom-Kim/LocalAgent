# Task/Job Queue Refactor Design

**Date:** 2026-03-29
**Status:** Draft

## Problem Statement

The current task system requires callers to specify all execution details upfront (`task_type`, `payload`, `executor`, `executor_model`). This tightly couples task submission to execution concerns. Callers must know which executor and model to use, which is both inconvenient and error-prone.

## Goals

1. **Decouple submission from execution:** Callers submit slim tasks (`task_type` + `payload` only). Execution details are resolved by the system.
2. **Introduce a task→job enrichment pipeline:** A new daemon reads raw tasks, applies enrichment rules from a YAML config, and produces enriched jobs.
3. **Separate queue topology:** Raw tasks and enriched jobs use distinct RabbitMQ queues.
4. **Maintain architectural consistency:** The new daemon follows the existing HTTP-polling pattern — no direct RabbitMQ access from daemons.

## Non-Goals

- Hot-reloading of enrichment config (restart-on-change is acceptable)
- Async/external enrichment lookups (YAML-only for now)
- Pattern-matching or regex-based task_type routing (simple key mapping)
- Additional enrichment fields beyond `executor` and `executor_model`

## Design

### Architecture Overview

```
Client
  │
  ▼
POST /tasks  {task_type, payload}
  │
  ▼
┌─────────────────────────────────────┐
│  API Service                        │
│                                     │
│  tasks queue  (sendToQueue)         │
│  jobs queue   (sendToQueue)         │
│  results exchange ──► lark-messages │
└─────────────────────────────────────┘
       │                    │
       ▼                    ▼
  Enrichment Daemon    Task Daemon
  (polls /tasks/next)  (polls /jobs/next)
       │                    │
       ▼                    ▼
  POST /jobs            POST /results
  (enriched job)        (job_id + task_id)
```

### Data Models

#### Task (slim — submitted by client)

```typescript
// Submission payload (client → API)
interface TaskSubmission {
  task_type: string;
  payload: string;
}

// Internal representation (API-generated fields added)
interface Task {
  task_id: string;        // UUID, generated by API
  task_type: string;
  payload: string;
  submitted_at: string;   // ISO timestamp
}
```

#### Job (enriched — produced by enrichment daemon)

```typescript
// Submission payload (enrichment daemon → API)
interface JobSubmission {
  task_id: string;          // Reference to original task
  task_type: string;
  payload: string;
  executor: TaskExecutorType;
  executor_model: string;
  submitted_at: string;     // Passed through from original task
}

// Internal representation (API-generated fields added)
interface Job {
  job_id: string;           // UUID, generated by API
  task_id: string;          // Reference to original task
  task_type: string;
  payload: string;
  executor: TaskExecutorType;
  executor_model: string;
  submitted_at: string;     // Original task submission time
  enriched_at: string;      // ISO timestamp of enrichment
}
```

#### TaskResult (updated to carry both IDs)

```typescript
interface TaskResultSubmission {
  job_id: string;
  task_id: string;
  status: ResultStatus;     // 'success' | 'failure'
  exit_code: number | null;
  stdout: string;
  stderr: string;
}

interface TaskResult extends TaskResultSubmission {
  result_id: string;        // UUID, generated by API
  completed_at: string;     // ISO timestamp
}
```

### RabbitMQ Topology

| Resource | Type | Name | Purpose |
|----------|------|------|---------|
| Queue | durable | `tasks` | Raw tasks awaiting enrichment (unchanged — no exchange, uses `sendToQueue`) |
| Queue | durable | `jobs` | Enriched jobs awaiting execution (new — no exchange, uses `sendToQueue`) |
| Exchange | fanout | `results` | Result distribution (unchanged) |
| Queue | durable | `lark-messages` | Lark notification queue (unchanged) |

The `tasks` queue continues to use direct `sendToQueue` publishing (no exchange), matching the current pattern. The new `jobs` queue follows the same pattern. The API's `RabbitMQService.connect()` method will assert the `jobs` queue on startup alongside the existing `tasks` queue.

### API Endpoints

#### Task Endpoints (modified)

| Method | Path | Description |
|--------|------|-------------|
| `POST /tasks` | Submit a slim task `{task_type, payload}` | Breaking change: `executor` and `executor_model` removed |
| `GET /tasks/next` | Poll for next raw task | Used by enrichment daemon |
| `POST /tasks/:id/ack` | Acknowledge raw task | Used by enrichment daemon after publishing job |

#### Job Endpoints (new)

| Method | Path | Description |
|--------|------|-------------|
| `POST /jobs` | Submit an enriched job | Used by enrichment daemon |
| `GET /jobs/next` | Poll for next job | Used by task-daemon (replaces `/tasks/next`) |
| `POST /jobs/:id/ack` | Acknowledge job completion | Used by task-daemon |

#### Result Endpoints (modified)

| Method | Path | Description |
|--------|------|-------------|
| `POST /results` | Submit a result | Body now includes `job_id` and `task_id` |
| `GET /results/next/:queueName` | Poll for results | Unchanged |
| `POST /results/:queueName/:id/ack` | Acknowledge result | Unchanged |

### Enrichment Daemon

#### Package Structure

```
├── src/

│   ├── enrichment-poller.ts   # Polls /tasks/next, enriches, publishes to /jobs
│   └── enrichment-service.ts  # YAML config loading + task→job mapping logic
├── test/
│   ├── enrichment-service.test.ts
│   └── enrichment-poller.test.ts
├── Dockerfile
├── package.json
├── tsconfig.json
└── .eslintrc.cjs
```

#### Enrichment YAML Config

Located at `packages/task-enrichment-daemon/config/enrichment.yaml`, overridable via `ENRICHMENT_CONFIG_PATH` env var.

```yaml
rules:
  code_review:
    executor: claude_code
    executor_model: opus
  quick_question:
    executor: claude_code
    executor_model: haiku
  default:
    executor: claude_code
    executor_model: sonnet
```

- The `default` key is optional but recommended. It is used when no specific rule matches the `task_type`.
- If no rule matches and no `default` is defined, the task is ACKed and logged as an error (rejected).

#### Enrichment Flow

1. `EnrichmentPoller` polls `GET /tasks/next` on the configured interval.
2. If a task is received, `EnrichmentService.enrich(task)` is called.
3. `EnrichmentService` looks up `task.task_type` in the YAML rules. Falls back to `default`.
4. If no rule matches: log error, ACK the task (remove from queue), return.
5. If a rule matches: validate that the `executor` and `executor_model` values are valid (exist in the shared `TASK_EXECUTORS` and `EXECUTOR_MODELS` constants). If invalid, log error, ACK the task, return.
6. Construct a `JobSubmission` with the task fields + enriched fields.
7. `POST /jobs` to publish the enriched job.
8. `POST /tasks/:id/ack` to acknowledge the raw task.

#### Error Handling

- **Unknown task_type, no default rule:** ACK task, log error. Task is consumed and lost (by design — user chose reject-and-log).
- **API unreachable (POST /jobs fails):** Do NOT ack the task. It stays in the queue for retry on next poll.
- **POST /jobs succeeds but POST /tasks/:id/ack fails:** The task remains in the queue and will be re-enriched on the next poll, producing a duplicate job. This is acceptable — downstream consumers (task-daemon) must already handle duplicate/idempotent execution since any at-least-once queue system can redeliver. Log a warning when ack fails.
- **API unreachable (GET /tasks/next fails):** Log warning, retry on next poll interval.

### Changes to Existing Packages

#### `packages/shared`

- **types.ts:** Remove `executor` and `executor_model` from `TaskSubmission` and `Task`. Add `Job`, `JobSubmission` types. Update `TaskResultSubmission` to include `job_id`.
- **constants.ts:** Add `DEFAULT_JOBS_QUEUE_NAME = 'jobs'`.

#### `packages/api`

- **rabbitmq.ts:** Assert `jobs` queue on connect (using `sendToQueue`, same pattern as existing tasks queue). Add `publishJob()`, `getNextJob()`, `ackJob()` methods (mirroring existing task methods).
- **routes/tasks.ts:** Update `POST /tasks` validation to only require `task_type` and `payload`.
- **routes/jobs.ts:** New route file with `POST /jobs`, `GET /jobs/next`, `POST /jobs/:id/ack`.
- **routes/results.ts:** Update `POST /results` validation to require both `job_id` and `task_id`.

#### `packages/task-daemon`

- **task-poller.ts:** Change to poll `GET /jobs/next` instead of `GET /tasks/next`. ACK via `POST /jobs/:id/ack`.
- **core/task-orchestrator.ts:** Accept `Job` type instead of `Task`.
- **adapters/claude-cli-executor.ts:** Accept `Job` type.
- **adapters/ttadk-executor.ts:** Accept `Job` type.
- **Result submission:** Include both `job_id` and `task_id` in `POST /results`.

#### `packages/lark-result-daemon`

- **lark-poller.ts:** Update to handle the new `TaskResult` shape that includes `job_id`.
- **adapters/lark-notifier.ts:** Include `job_id` in Lark notification messages alongside `task_id`.

### Docker Compose

```yaml
task-enrichment-daemon:
  build:
    context: .
    dockerfile: packages/task-enrichment-daemon/Dockerfile
  environment:
    - API_URL=http://api:3000
    - POLL_INTERVAL_MS=5000
    - LOG_LEVEL=info
  depends_on:
    rabbitmq:
      condition: service_healthy
    api:
      condition: service_started
  profiles:
    - task-enrichment-daemon
    - full
```

### Message Flow Summary

```
1. Client ──POST /tasks──► API ──sendToQueue──► tasks queue
2. Enrichment Daemon ──GET /tasks/next──► API ──get──► tasks queue
3. Enrichment Daemon ──enrich(task)──► JobSubmission
4. Enrichment Daemon ──POST /jobs──► API ──sendToQueue──► jobs queue
5. Enrichment Daemon ──POST /tasks/:id/ack──► API ──ack──► tasks queue
6. Task Daemon ──GET /jobs/next──► API ──get──► jobs queue
7. Task Daemon ──execute(job)──► result
8. Task Daemon ──POST /results──► API ──publish──► results exchange
9. Task Daemon ──POST /jobs/:id/ack──► API ──ack──► jobs queue
10. Lark Daemon ──GET /results/next/lark-messages──► processes result with job_id + task_id
```

## Testing Strategy

### Enrichment Daemon Tests

- **enrichment-service.test.ts:**
  - Loads valid YAML config
  - Maps known task_type to correct executor/model
  - Falls back to `default` for unknown task_type
  - Returns null/error when no default rule and unknown task_type
  - Validates executor/model values against known valid values

- **enrichment-poller.test.ts:**
  - Polls and enriches a task successfully
  - Handles no-task-available (null response)
  - Does not ACK task when POST /jobs fails
  - ACKs and logs when enrichment fails (no matching rule)
