# Task Queue System — Design Specification

**Date:** 2026-03-26
**Status:** Draft

## 1. Overview

A task queue system where tasks are submitted via an HTTP API to RabbitMQ, and a local daemon polls the API to consume and process them. The system is deployed using docker-compose (API + RabbitMQ), while the daemon runs natively on the host machine.

### 1.1 Goals

- Submit tasks via HTTP API to RabbitMQ
- Daemon polls HTTP API to retrieve and process tasks
- Manual ACK flow: RabbitMQ waits for explicit client acknowledgment before removing messages
- Deployable via `docker-compose up` (API + RabbitMQ)
- Rush 5 / TypeScript monorepo structure

### 1.2 Non-Goals

- Authentication / authorization
- Multiple concurrent task processing
- Multi-instance API deployment
- Task persistence beyond RabbitMQ's durability
- UI / dashboard

## 2. Architecture

```
┌─────────────┐     HTTP POST      ┌─────────────┐     AMQP publish    ┌─────────────┐
│   Client /   │ ──────────────────>│   API        │ ──────────────────>│  RabbitMQ    │
│   Submitter  │                    │  (Express)   │<──────────────────>│  (Docker)    │
└─────────────┘                    └──────┬───────┘     AMQP consume    └─────────────┘
                                          │ HTTP
                                          │ GET /tasks/next
                                          │ POST /tasks/:id/ack
                                   ┌──────┴───────┐
                                   │   Daemon      │
                                   │  (Host OS)    │
                                   └──────────────┘
```

### 2.1 Components

#### API Server (`packages/api`)
- **Framework:** Express on Node 20
- **Responsibility:** HTTP bridge over RabbitMQ
- **Behavior:**
  - On startup, connects to RabbitMQ via amqplib, asserts a durable queue `tasks`
  - `POST /tasks` — accepts `{ task_type, payload }`, publishes to RabbitMQ queue with `persistent: true`. Returns `201` with `{ task_type, payload, submitted_at }`.
  - `GET /tasks/next` — pulls one message from the queue using `channel.get()` (pull-based, not consumer-based). Stores the AMQP delivery tag in an in-memory `Map<taskId, deliveryInfo>`. Returns the task with a generated UUID as `task_id`. If queue is empty, returns `204 No Content`.
  - `POST /tasks/:id/ack` — looks up the delivery tag from the in-memory map, ACKs the message in RabbitMQ, removes from map. Returns `200 OK` or `404` if task ID unknown.
  - `GET /health` — returns `200` with RabbitMQ connection status
- **Runs in:** Docker container (docker-compose)

#### Daemon (`packages/daemon`)
- **Responsibility:** Polls the API, processes tasks, ACKs them
- **Behavior:**
  - Polls `GET /tasks/next` every N seconds (configurable via `POLL_INTERVAL_MS`, default 5000)
  - On receiving a task: logs the task payload via pino, then calls `POST /tasks/:id/ack`
  - Processes one task at a time (sequential)
  - Graceful shutdown on SIGINT/SIGTERM
- **Runs on:** Host machine (outside Docker), or optionally inside Docker

#### Shared Library (`packages/shared`)
- **Contents:**
  - TypeScript interfaces: `Task`, `TaskSubmission`
  - Shared utilities: pino logger factory, config loader (dotenv)
  - Constants: queue names, default config values

### 2.2 Task Schema

```typescript
interface TaskSubmission {
  task_type: string;  // Currently always "generic"
  payload: string;    // Arbitrary string payload
}

interface Task {
  task_id: string;    // UUID generated by API on consumption
  task_type: string;
  payload: string;
  submitted_at: string; // ISO 8601 timestamp
}
```

### 2.3 API Endpoints

| Method | Path | Request Body | Response | Description |
|--------|------|-------------|----------|-------------|
| POST | /tasks | `{ task_type, payload }` | `201 { task_type, payload, submitted_at }` | Submit a task |
| GET | /tasks/next | — | `200 { task_id, task_type, payload, submitted_at }` or `204` | Poll next task |
| POST | /tasks/:id/ack | — | `200 { acknowledged: true }` or `404` | Acknowledge a task |
| GET | /health | — | `200 { status, rabbitmq }` | Health check |

### 2.4 RabbitMQ Configuration

- **Queue name:** `tasks`
- **Durable:** `true` (survives RabbitMQ restart)
- **Message persistence:** `deliveryMode: 2` (persistent)
- **Consumption method:** `channel.get()` (pull-based, one message per API request)
- **Manual ACK:** `noAck: false` passed to `channel.get()`
- **Unacked message behavior:** If the API process restarts, the AMQP connection closes and RabbitMQ automatically requeues any unACKed messages

### 2.5 In-Memory Delivery Tag Map

The API maintains a `Map<string, { channel, deliveryTag, timestamp }>`:

- **Key:** Generated UUID (`task_id`)
- **Value:** AMQP channel reference and delivery tag needed to ACK
- On `GET /tasks/next`: entry is added
- On `POST /tasks/:id/ack`: entry is removed after ACKing
- On API restart: map is lost, but RabbitMQ redelivers unACKed messages automatically

This is intentionally simple. No cleanup is needed because:
1. The daemon processes one task at a time and ACKs promptly
2. If the API crashes, RabbitMQ handles redelivery
3. The map grows by at most 1 entry at a time in normal operation

```yaml
services:

      RABBITMQ_DEFAULT_USER: guest
      RABBITMQ_DEFAULT_PASS: guest
    healthcheck:
      test: rabbitmq-diagnostics -q ping
      interval: 10s
      timeout: 5s
      retries: 5

  api:
    build:
      context: .
      dockerfile: packages/api/Dockerfile
    ports:
      - "3000:3000"
    environment:
      RABBITMQ_URL: amqp://guest:guest@rabbitmq:5672
    depends_on:
      rabbitmq:
        condition: service_healthy
```

The daemon is NOT in docker-compose — it runs on the host and connects to `http://localhost:3000`.

## 6. Error Handling

- **API cannot connect to RabbitMQ:** Retry with exponential backoff on startup. `/health` reports unhealthy.
- **Daemon cannot reach API:** Log error, continue polling at normal interval.
- **Daemon crashes mid-task:** The delivery tag is held in the API's in-memory map and the AMQP channel remains open. The message stays unACKed in RabbitMQ until the API restarts (which closes the channel, triggering redelivery). Since `channel.get()` is used (no consumer), there is no consumer timeout. In practice, the map entry becomes orphaned but the next API restart clears it.
- **API crashes:** All unACKed messages return to queue. Daemon polls get errors until API is back up.
- **Malformed task submission:** 400 response with validation error.

## 8. Testing Strategy

- **Unit tests:** Each package has its own Vitest config. Test business logic (handler, config parsing, route handlers with mocked RabbitMQ).
- **Integration tests:** Test API endpoints with a real RabbitMQ instance (can use docker-compose for CI).
- **Manual testing:** `curl` commands to submit tasks and verify daemon picks them up.
